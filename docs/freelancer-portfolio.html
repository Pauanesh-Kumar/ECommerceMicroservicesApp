Architecture

Clients reach User through the YARP gateway and call Product and Cart directly. Cart starts checkout over HTTP, then Order, Product, Payment, Notification and Analytics cooperate through Kafka events.

One order, step by step

  1. Cart starts checkout

    Reads the signed-in user, calls Order over HTTP and generates an idempotency key if the client sent none. A client that retries should send a stable key.

  2. Order writes once

    The order, the idempotency record and an order-created outbox row are saved in a single database save, so a crash cannot leave one without the others.

  3. Kafka fans out

    The outbox publisher sends the event. Product reserves stock, Payment opens a provider order, Notification and Analytics record it.

  4. Payment settles

    Razorpay reports the result by signed webhook. A background reconciler asks the provider about payments left uncertain, then publishes the outcome through Payment’s own outbox.

  5. Order completes or compensates

    The saga consumer saves its inbox entry, the state change and the next outbox row together, then commits the Kafka offset.

Reliability decisions

Idempotent order creation

A database-backed idempotency key makes a repeated checkout return the first result instead of a second order.

Transactional outbox and inbox

State change and message are committed together; consumers record event IDs so at-least-once delivery does not double-apply.

Oversell-safe inventory

Reservation, per-order state, inbox and outbox change in one MongoDB transaction with snapshot reads and majority writes.

Uncertain is not failed

A payment saved as Initiating is never retried by POST. The reconciler matches receipt, amount and currency before acting.

Backoff, not skipping

Failed records are retried with exponential delay up to 30 seconds; offsets only advance after success.

Signed webhooks

Razorpay signatures are verified, and repeated or concurrent webhooks are handled by a status concurrency token.

Verification

Failure scenarios rehearsed on disposable infrastructure

  • Checkout and insufficient stock
  • Failed, then captured, payment
  • Missed webhook recovered by reconciliation
  • Database failures and process restarts
  • Concurrent webhooks and duplicate event replay

A C# harness starts five APIs with disposable Kafka, PostgreSQL, a MongoDB replica set, Redis and a Razorpay-compatible stub, then checks the outcome of each scenario. Seven xUnit projects cover domain behavior, checkout, payment processing, validation and analytics limits, and Product inventory transactions have their own replica-set tests for rollback, duplicates and conflicting event IDs.
